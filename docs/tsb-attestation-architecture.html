Make the signature mean something.

A concrete design for turning NautGate’s Securosys TSB extension from a manual digest signer into independently verifiable routing evidence—and an HSM-enforced authorization boundary for consequential agent actions.

01 / Current truth

Today’s signature is real. Its claim is weak.

The HSM genuinely signs 32 bytes, but NautGate does not automatically construct and sign a complete routing decision. The chain-head endpoint covers only sensitive privacy-log entries and must be invoked explicitly.

Honest status

An optional generic HSM-signing sidecar and manual privacy-chain sealing prototype. It is not yet operational per-decision attestation.

1

Locally hashed

Sensitive prompt content plus a small set of privacy-log fields are SHA-256 hashed into a chain.

2

Remotely signed

The latest 32-byte chain-head digest is sent to TSB and signed by the key inside the Securosys HSM.

3

Not yet bound

Response, route, observed model, cost, build, configuration and policy are not bound into that signature.

02 / What to sign

Two objects. Two security properties.

Evidence after a call and permission before an action are different problems. Treating them as one produces either unnecessary latency or security theatre.

AFTER THE EVENTNON-BLOCKING

Decision receipt

Proves what NautGate received, classified, selected, observed and accounted for. Signed asynchronously after the provider response is finalized.

BEFORE EXECUTIONBLOCKING

Execution authorization

Binds a specific high-risk tool action to an SKA approval policy. The action cannot execute until the required approval is satisfied.

Core rule: do not sign arbitrary caller-provided digests with unsigned metadata. NautGate must construct a versioned, canonical, domain-separated envelope and sign that exact representation.
03 / Evidence envelope

The public receipt contains hashes—not prompt text, response text, credentials or bearer tokens. An operator can later disclose source material and prove it matches the signed evidence.

Canonical

RFC 8785 JSON Canonicalization Scheme or deterministic CBOR. One encoding is normative; there is no signature over ordinary serializer output.

Domain-separated

NAUTGATE-DECISION-RECEIPT-V1\0 prefixes the canonical bytes, preventing reuse as another document type.

Failure-complete

Timeouts, billing failures, policy denial and malformed upstream responses produce receipts too. Evidence cannot cover only successes.

05 / Key architecture

One key per meaning—not one key per sidecar.

Key identityPurposePolicyTraffic impact
nautgate-attestation-v1Decision receipts and Merkle checkpointsAutomated service authorization; strict NautGate workload identityAsynchronous, never blocks model response
nautgate-execution-approval-v1Pre-execution authorization envelopesSKA: automated policy OR/AND named human approvers; optional timelockBlocks only protected actions
nautgate-release-v1Release artifacts, containers and policy bundlesRelease-manager threshold approvalRelease pipeline only
nautgate-audit-anchor-v1Daily/weekly long-term audit rootsRestricted scheduled service identityBackground only

The key identifier and version are part of every signed envelope. Rotation creates a new version; old public keys and certificates remain available for historical verification.

06 / Verification contract

Verification must not trust NautGate.

A signature stored beside an editable row in the same database is not yet a usable product. Exported evidence must be independently and deterministically verifiable.

Receipt bundle

Canonical envelope, signature, algorithm, key ID/version, certificate chain or stable reference, checkpoint, Merkle inclusion proof and trusted timestamp where required.

Offline command

nautgate receipt verify receipt.json reconstructs bytes, validates hashes and proof, checks the certificate and prints the exact claim covered.

  • Verification succeeds without NautGate or TSB network access.
  • Changing any signed field fails verification.
  • Changing disclosed prompt/response material fails its hash check.
  • Unknown schemas fail closed.
  • Unknown, revoked or wrong-purpose keys fail closed.
  • Duplicate sequence or nonce consumption is detectable.
  • Missing checkpoint windows raise an audit gap.
  • Database timestamps are not presented as trusted time.
07 / Delivery plan

Build evidence before policy theatre.

Receipt specification

Freeze schema, canonicalization, domain prefix, privacy rules and test vectors.

FOUNDATION

Core capture + outbox

Finalize success and failure receipts transactionally; expose honest signing states.

OPERATIONAL

Checkpoint signer

Merkle batching, TSB signatures, idempotent retry, gap alarms and key rotation.

AT SCALE

Independent verifier

Portable bundle, CLI verification, published public-key history and conformance suite.

TRUSTABLE

SKA action gate

Canonical execution intents, approval policy mapping, expiry and one-time nonce enforcement.

ENFORCED
Definition of done

A third party can prove which request was handled, which route was selected, which model actually answered, what result was recorded and which NautGate build and policy produced the decision. A protected tool action cannot run without an HSM-enforced approval over that exact action.
