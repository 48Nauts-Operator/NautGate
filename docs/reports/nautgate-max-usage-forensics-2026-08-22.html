Why Claude Max usage collapsed on 22 August

A read-only investigation of NautGate's audit trail for the pi agent, focused on Claude Code-shaped sessions, Max-plan routing, context growth, request frequency, and prompt-cache behavior.

High-confidence verdict

A new Max-subscription route exposed two rapidly growing agentic sessions to Claude Opus without effective prompt caching. The result was 148.53 million fresh Opus input tokens in one day—42.8× the previous day's volume.

What changed

20 August, commit 4ad7157: “a Claude Max lane for ordinary ng_ clients.”

Before this change, ordinary NautGate-key traffic from pi did not successfully consume the operator's Claude Max subscription. After the change, NautGate supplied the operator's Claude OAuth credential to NautRouter and sent explicit Claude model requests to the Max lane.

What NautGate proves High confidence

  • Both sessions authenticated as agent pi.
  • Both originated from 127.0.0.1 / localhost.
  • Both used the Anthropic inbound format and explicitly requested claude-opus-5.
  • The tool schemas are Claude Code-compatible: Bash and a large coding-agent tool surface.
  • The conversation content repeatedly references xNaut, Papers/MCP, Librarian, canvas, panes, screenshots, and local product work.

What NautGate cannot prove Attribution gap

  • The exact local process, PID, executable path, bundle ID, or window that opened the connection.
  • Which of 33 historical pi API keys was used; decisions do not retain a key ID.
  • The key had no project assignment on these calls.
  • NautGate's session ID is a content-derived heuristic, not Claude Code's native session UUID.

Best-supported attribution: a local xNaut/Pi integration hosting or driving Claude Code-style agents. The downstream model was Claude Opus 5, but NautGate cannot yet name the precise xNaut surface or local process.

Why prompt caching failed

  1. The affected requests traveled through the ordinary ng_ client route added on 20 August.
  2. NautRouter translated the request for Anthropic and added the Claude Code identity block needed for OAuth access.
  3. The translator did not add Anthropic cache_control markers to the system, tools, or stable history prefix.
  4. NautGate recorded zero cache reads and zero cache writes across the affected sessions.
  5. As the sessions grew, each subsequent request retransmitted hundreds of thousands of fresh tokens.

Five-hour and weekly limits

The recorded traffic is sufficient to explain rapid Max-plan depletion: hundreds of uncached Opus calls, reaching 148.53M fresh input tokens in one day. NautGate observed substantial activity gaps, including 16:06–17:53 and 19:30–23:49.

NautGate did not record upstream 429 responses for the affected calls, so those gaps cannot be formally labeled as quota windows. The client may have stopped before reaching NautGate or handled the plan limit outside the captured response path. NautGate also does not capture Anthropic's account-level remaining percentage or internal quota weighting.

Continuing exposure

23 August warning

By the time of investigation, pi had already sent another 45.84M fresh Opus input tokens across 96 calls, averaging 477K fresh tokens per call. The condition was still active.

Recommended controls

  1. Immediate: stop or cap the uncached Opus route for pi until prompt caching is correctly implemented.
  2. Cache correctness: preserve or generate stable Anthropic cache breakpoints for system, tools, and conversation prefixes.
  3. Velocity alerts: warn or pause when a session exceeds thresholds such as 100K fresh tokens per call or 5M fresh tokens per hour.
  4. Attribution: write API key ID/name, project, client app, native session ID, and optional PID into every decision.
  5. Session controls: expose context growth, calls per user turn, interruption loops, and cache-hit ratio in the dashboard.
  6. Subscription isolation: require explicit per-key authorization before a normal NautGate client may spend Claude Max quota.
